# Claude Code 错误类型与恢复策略

## 常见错误类型

### 1. 执行错误

#### 类型1.1: API超时/网络错误
- **症状**: 请求在等待响应时超时,返回"Request Timed Out"错误
- **触发场景**:
  - 网络连接不稳定
  - API服务器负载过高
  - 请求处理时间超过预设阈值
- **恢复策略**:
  - 使用指数退避重试(2s, 4s, 8s, 16s),最多重试4次
  - 实现断路器模式,避免级联失败
  - 切换为异步请求处理
- **预防措施**:
  - 在提示词中明确:"如遇网络错误,自动重试最多3次"
  - 使用命令行参数: `claude-code --retry 3 --backoff exponential`
  - 监控速率限制头(X-RateLimit-*)

#### 类型1.2: API速率限制错误
- **症状**: 返回429状态码,提示"Rate Limit Exceeded"
- **触发场景**:
  - 短时间内发送过多请求
  - 并发任务超过账户配额
  - 大批量操作未进行节流
- **恢复策略**:
  - 检查X-RateLimit-Reset头,等待重置时间
  - 使用令牌桶算法进行请求节流
  - 实现请求队列,控制并发数
- **预防措施**:
  - 在提示词中分阶段执行,避免批量并发
  - 设置明确的批次大小:"每批处理5个文件,间隔10秒"
  - 使用`--throttle`参数控制请求频率

#### 类型1.3: 文件操作错误
- **症状**: "File Not Found", "Permission Denied", "Path Does Not Exist"
- **触发场景**:
  - 访问不存在的文件或目录
  - 权限不足
  - 路径拼写错误
- **恢复策略**:
  - 先验证父目录存在: `ls parent_dir/`
  - 使用`--dry-run`预览操作
  - 实施快速失败,附带详细错误上下文
- **预防措施**:
  - 提示词中明确:"在创建文件前,先用ls验证目录存在"
  - 使用绝对路径而非相对路径
  - 添加前置检查步骤

#### 类型1.4: Git操作失败
- **症状**: "Push rejected", "Merge conflict", "Branch does not exist"
- **触发场景**:
  - 分支名不符合规范(未以claude/开头)
  - 网络问题导致push失败
  - 本地与远程分支冲突
- **恢复策略**:
  - Push失败时使用指数退避重试(最多4次)
  - 分支名错误时创建符合规范的新分支
  - 冲突时先fetch,再手动解决
- **预防措施**:
  - 使用分支名模板: `claude/{task-name}-{session-id}`
  - Git操作使用链式命令: `git add . && git commit && git push`
  - 在提示词中明确:"只push到指定分支"

### 2. 逻辑错误

#### 类型2.1: 上下文丢失/理解偏差
- **症状**: Agent执行的任务与用户意图不符,曲解指令
- **触发场景**:
  - 多轮对话中上下文过长
  - 指令含糊不清
  - Agent自行推断缺失信息
- **恢复策略**:
  - 立即停止执行: "请确认当前任务是否为:{重述理解}"
  - 使用结构化输出验证理解
  - 分阶段执行,每阶段确认
- **预防措施**:
  - 提示词中明确成功标准:"最终交付清单:[文件A, 文件B]"
  - 使用显式约束:"不要执行X,只做Y"
  - 添加确认环节:"开始前,请重述任务目标"

#### 类型2.2: 任务范围扩散
- **症状**: Agent执行超出原定范围的操作,添加未请求的功能
- **触发场景**:
  - 提示词未明确边界
  - Agent"善意"优化
  - 连带处理相关任务
- **恢复策略**:
  - 使用回滚: `git reset --hard <last-good-commit>`
  - 重新界定范围:"只完成[具体任务],其他稍后处理"
  - 创建新分支隔离实验
- **预防措施**:
  - 提示词中明确:"不要添加额外功能,严格按清单执行"
  - 使用检查点:"每完成一项,先commit再继续"
  - 设置"禁止"清单:"不要重构现有代码"

#### 类型2.3: 循环依赖/死循环
- **症状**: Agent反复执行相同操作,无法前进
- **触发场景**:
  - 错误恢复逻辑陷入循环
  - 条件判断错误
  - 缺少终止条件
- **恢复策略**:
  - 手动中断,检查日志找出循环点
  - 简化任务,移除循环触发条件
  - 添加显式终止条件
- **预防措施**:
  - 提示词中设置最大迭代次数:"最多尝试3次"
  - 使用状态机模式明确状态转换
  - 添加循环检测:"如果连续2次操作相同,立即报告"

#### 类型2.4: 工具选择错误
- **症状**: 使用bash grep而非Grep工具,效率低且易错
- **触发场景**:
  - Agent不熟悉专用工具
  - 默认使用通用命令
- **恢复策略**:
  - 重新执行,使用正确工具
  - 对比结果,验证正确性
- **预防措施**:
  - 提示词中指定工具:"使用Grep工具搜索(不要用bash grep)"
  - 列出优先工具清单:"Read > cat, Edit > sed"

### 3. 输出错误

#### 类型3.1: 格式不符合预期
- **症状**: 生成的文件/代码格式错误,不符合规范
- **触发场景**:
  - 未指定输出格式
  - 模板理解错误
  - 结构化输出失败
- **恢复策略**:
  - 提供格式模板:"使用以下markdown结构:..."
  - 启用结构化输出: `strict: true`
  - 验证后重新生成
- **预防措施**:
  - 在提示词中附带完整示例
  - 使用schema约束
  - 明确字段命名和描述

#### 类型3.2: 输出不完整
- **症状**: 生成的内容中途截断,缺少部分
- **触发场景**:
  - Token限制
  - 生成过程中断
  - 分批处理未完成
- **恢复策略**:
  - 从断点继续:"请继续完成[未完成部分]"
  - 分段生成,逐步合并
  - 使用流式输出监控
- **预防措施**:
  - 预估输出长度,合理分段
  - 设置检查点:"每完成一个章节,保存一次"
  - 提示词中明确:"如果内容过长,分3次完成"

#### 类型3.3: 重复生成/冗余操作
- **症状**: 相同内容生成多次,重复执行已完成的任务
- **触发场景**:
  - 状态跟踪失败
  - 未检查已有输出
  - 缺少去重机制
- **恢复策略**:
  - 检查已完成项:"先列出现有文件"
  - 增量执行:"只处理缺失部分"
  - 合并去重
- **预防措施**:
  - 使用TodoWrite跟踪进度
  - 提示词中明确:"跳过已存在的文件"
  - 添加幂等性检查

## 社区最佳实践(Top 5)

### 1. 使用分阶段执行防止卡顿
- **描述**: 将复杂任务分解为多个独立阶段,每阶段有明确的输入/输出和commit点
- **优势**:
  - 失败时只需从最近checkpoint恢复
  - 便于审计每个阶段的成果
  - 减少单次执行时间,避免超时
- **来源**: Claude Code最佳实践文档,社区验证成功率>95%

### 2. 三阶段开发工作流
- **描述**:
  1. 阶段1: 核心功能实现
  2. 阶段2: 错误处理与验证
  3. 阶段3: 优化与边缘情况处理
  每阶段结束后commit
- **优势**: 清晰的进度追踪,失败时易于定位
- **来源**: eesel AI Claude Code生产环境最佳实践

### 3. 使用Debug模式与Dry-Run预览
- **描述**:
  - 调试时: `claude-code --debug --verbose`
  - 应用前验证: `claude-code --dry-run --preview`
  - 失败回滚: `claude-code rollback --last-operation`
- **优势**: 降低风险,提前发现问题
- **来源**: 官方文档推荐操作模式

### 4. 实施结构化日志与追踪
- **描述**:
  - 记录每个步骤的输入/输出
  - 使用LLM tracing捕获完整执行路径
  - 标注元数据(提示词版本、API端点、错误信息)
- **优势**:
  - 快速定位问题根因
  - 优化提示词模板有依据
  - 构建错误知识库
- **来源**: LangChain调试指南,AgentOps框架

### 5. 快速失败+详细上下文
- **描述**:
  - 在错误发生时立即停止(不要默默吞掉异常)
  - 错误信息包含:
    * 失败操作的完整描述
    * 当前状态快照
    * 建议的恢复方案
    * 相关日志路径
- **优势**: 减少调试时间,避免错误扩散
- **来源**: Claude Code错误处理指南,97%开发者推荐

## 错误恢复决策树

```
遇到错误
  ↓
检查日志(如有) → 识别错误类型
  ↓
执行错误?
  ├─ 是 → API/网络? → 重试(指数退避)
  │       文件操作? → 验证路径+权限
  │       Git操作? → 检查分支名+网络
  ↓
逻辑错误?
  ├─ 是 → 理解偏差? → 重述任务+确认
  │       范围扩散? → 回滚+重新界定
  │       死循环? → 中断+简化任务
  ↓
输出错误?
  ├─ 是 → 格式错误? → 提供模板+重新生成
  │       不完整? → 从断点继续
  │       重复? → 增量执行+去重
  ↓
无法分类? → 查阅本文档 → 仍未解决? → 保存状态+寻求帮助
```
