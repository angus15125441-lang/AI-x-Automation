# Claude Code 标准提示范式集

## 使用说明

- **定制标记**: 每个模板用 `{占位符}` 标记需要定制的部分,使用时替换为实际内容
- **复杂度等级**:
  - 🟢 简单: 单文件操作、快速任务(<5分钟)
  - 🟡 标准: 多步骤、需要日志(10-30分钟)
  - 🔴 复杂: 多阶段、网络搜索、需要审计(>30分钟)
- **选择建议**: 根据任务类型和复杂度查看文末的"模板选择指南"

## 1. 操作说明型提示词

### 模板1.1: 基础任务执行 🟢

**适用场景**: 单文件编辑、简单脚本执行、配置修改

**模板**:
```markdown
请完成以下任务: {任务描述}

执行要求:
- 在开始前,说明"正在执行: {任务名}"
- 在每个关键步骤前,说明"步骤X: {步骤描述}"
- 在每个步骤后,说明"已完成步骤X,结果: {结果摘要}"
- 如果遇到错误,立即说明:"错误类型: {类型},原因: {分析},建议: {恢复方案}"

预期输出: {描述最终产出,如"修改后的config.json文件"}

成功标准:
- [ ] {标准1,如"文件语法正确"}
- [ ] {标准2,如"配置项符合规范"}
```

**使用示例**:
```markdown
请完成以下任务: 在package.json中添加新的依赖项"axios": "^1.6.0"

执行要求:
- 在开始前,说明"正在执行: 添加axios依赖"
- 在每个关键步骤前,说明"步骤X: {步骤描述}"
- 在每个步骤后,说明"已完成步骤X,结果: {结果摘要}"
- 如果遇到错误,立即说明:"错误类型: {类型},原因: {分析},建议: {恢复方案}"

预期输出: 更新后的package.json文件,axios已添加到dependencies

成功标准:
- [ ] package.json语法正确(有效的JSON)
- [ ] axios版本为^1.6.0
- [ ] 文件其他部分未被修改
```

### 模板1.2: 分阶段任务执行 🟡

**适用场景**: 多步骤任务、需要防止卡顿、可能遇到中间错误

**模板**:
```markdown
请分阶段完成以下任务: {任务总体描述}

【阶段1: {阶段1名称}】
任务:
- {子任务1}
- {子任务2}

执行后:
git add {相关文件} && git commit -m "阶段1完成-{简短描述}"

【阶段2: {阶段2名称}】
任务:
- {子任务1}
- {子任务2}

执行后:
git add {相关文件} && git commit -m "阶段2完成-{简短描述}"

【阶段N: ...】
[重复结构]

执行建议:
1. 严格按阶段顺序执行,一个阶段完成后再开始下一个
2. 每个阶段结束必须commit,即使有错误也先保存已完成部分
3. 如果某阶段遇到错误,不要继续下一阶段,先报告问题

最终交付:
- [ ] {交付物1}
- [ ] {交付物2}
- [ ] 所有阶段的commit记录清晰
```

**使用示例**:
```markdown
请分阶段完成以下任务: 重构用户认证模块,分离逻辑和数据层

【阶段1: 创建新的目录结构】
任务:
- 创建 src/auth/logic/ 目录
- 创建 src/auth/data/ 目录
- 创建 src/auth/types.ts 用于共享类型定义

执行后:
git add src/auth/ && git commit -m "阶段1完成-目录结构创建"

【阶段2: 提取数据层】
任务:
- 将所有数据库操作移至 data/userRepository.ts
- 导出清晰的接口函数
- 添加类型注解

执行后:
git add src/auth/data/ && git commit -m "阶段2完成-数据层提取"

【阶段3: 重构业务逻辑】
任务:
- 将认证逻辑移至 logic/authService.ts
- 调用数据层接口而非直接操作数据库
- 确保测试通过

执行后:
git add src/auth/logic/ && git commit -m "阶段3完成-业务逻辑重构"

执行建议:
1. 严格按阶段顺序执行,一个阶段完成后再开始下一个
2. 每个阶段结束必须commit,即使有错误也先保存已完成部分
3. 如果某阶段遇到错误,不要继续下一阶段,先报告问题

最终交付:
- [ ] src/auth/目录结构清晰(logic/data分离)
- [ ] 所有文件有完整类型注解
- [ ] 现有测试仍然通过
- [ ] 3个清晰的阶段commit
```

### 模板1.3: 工具指定型任务 🟢

**适用场景**: 需要明确使用专用工具而非bash命令

**模板**:
```markdown
请完成: {任务描述}

工具使用要求:
- 搜索代码: 使用Grep工具(不要用bash grep)
- 读取文件: 使用Read工具(不要用cat)
- 编辑文件: 使用Edit工具(不要用sed/awk)
- 查找文件: 使用Glob工具(不要用find)

执行步骤:
1. {步骤1} - 使用工具: {指定工具}
2. {步骤2} - 使用工具: {指定工具}
3. ...

预期输出: {最终产出}
```

**使用示例**:
```markdown
请完成: 在所有React组件中查找使用了useState但未设置初始值的情况

工具使用要求:
- 搜索代码: 使用Grep工具(不要用bash grep)
- 读取文件: 使用Read工具(不要用cat)
- 编辑文件: 使用Edit工具(不要用sed/awk)
- 查找文件: 使用Glob工具(不要用find)

执行步骤:
1. 查找所有.tsx和.jsx文件 - 使用工具: Glob
2. 搜索useState模式 - 使用工具: Grep(pattern="useState\(\)")
3. 读取匹配文件检查初始值 - 使用工具: Read
4. 生成报告列出所有问题文件

预期输出: 一个markdown报告,列出所有未设置useState初始值的文件和行号
```

## 2. 错误恢复型提示词

### 模板2.1: 错误分析与恢复 🟡

**适用场景**: 任务执行失败需要诊断和恢复

**模板**:
```markdown
刚才的执行出现了问题,请按以下步骤恢复:

## 1. 错误诊断

请检查:
- 最后一次成功的操作是什么?
- 在哪个环节出错? (文件名/行号/操作类型)
- 错误类型是什么? (参考error-types-and-recovery.md分类)
  * 执行错误(API/网络/文件/Git)?
  * 逻辑错误(理解偏差/范围扩散/死循环)?
  * 输出错误(格式/不完整/重复)?
- 具体错误信息/日志是什么?

## 2. 恢复方案

基于错误类型,采取对应策略:

**如果是执行错误**:
- API超时/网络错误 → 重试3次(指数退避: 2s, 4s, 8s)
- 文件操作错误 → 验证路径和权限,使用绝对路径
- Git操作失败 → 检查分支名(是否以claude/开头),检查网络

**如果是逻辑错误**:
- 理解偏差 → 重述任务目标,请我确认
- 范围扩散 → 回滚到上一个commit,重新界定范围
- 死循环 → 简化任务,移除循环触发条件

**如果是输出错误**:
- 格式不符 → 提供格式模板和示例
- 内容不完整 → 从断点继续,分段生成
- 重复生成 → 检查已完成项,仅处理缺失部分

## 3. 恢复执行

具体恢复步骤:
1. 保存当前状态(如未保存): git add . && git commit -m "错误前保存-{时间戳}"
2. 执行恢复操作: {具体命令/操作}
3. 从{哪个阶段/步骤}重新开始
4. 记录本次错误到日志: logs/{task-name}-errors.md

## 4. 预防措施

为避免再次出错,调整策略:
- 提示词优化: {如何改进}
- 设置检查点: 每{X}步commit一次
- 添加验证: 在{哪里}增加前置检查

请按以上步骤执行恢复。
```

### 模板2.2: 任务范围重新界定 🟢

**适用场景**: 任务偏离目标或范围扩散时纠正

**模板**:
```markdown
请停止当前执行,重新界定任务范围:

## 原定任务
{原始任务描述}

## 当前问题
我注意到执行出现了以下偏差:
- {偏差1,如"添加了未请求的功能X"}
- {偏差2,如"修改了不应该动的文件Y"}

## 重新界定范围

**只做**:
1. {明确的任务1}
2. {明确的任务2}
3. {明确的任务3}

**不要做**:
- ❌ {禁止操作1}
- ❌ {禁止操作2}
- ❌ 任何未在"只做"清单中列出的操作

**成功标准** (精确):
- [ ] {可验证的标准1}
- [ ] {可验证的标准2}

## 恢复方式

如果已经执行了超出范围的操作:
1. 检查Git状态: git status
2. 回滚不必要的更改: git reset --hard {last-good-commit}
3. 或创建新分支隔离: git checkout -b {task-name-simplified}

重新开始,严格按"只做"清单执行,完成一项commit一次。
```

### 模板2.3: 循环检测与中断 🟢

**适用场景**: Agent反复执行相同操作时强制终止

**模板**:
```markdown
检测到可能的循环执行,请立即停止并分析:

## 循环检测

请检查最近{N}次操作(如5次):
- 是否重复执行相同的命令/工具调用?
- 是否反复遇到相同的错误?
- 是否在两个状态之间来回切换?

如果是,说明:"检测到循环,类型: {描述循环模式}"

## 根因分析

可能的原因:
- [ ] 错误恢复逻辑本身有问题(恢复后又触发同样错误)
- [ ] 条件判断错误(期望的条件永远不满足)
- [ ] 缺少终止条件(没有设置最大尝试次数)
- [ ] 外部依赖问题(如API持续返回错误)

确定根因: {具体是哪个原因}

## 中断与简化

立即执行:
1. 停止当前循环操作
2. 保存当前状态: git add . && git commit -m "循环中断-保存现场"
3. 简化任务:
   - 原任务: {完整描述}
   - 简化为: {去掉导致循环的部分}
   - 或分解为: {更小的子任务}

4. 添加终止条件:
   - 最多尝试{X}次
   - 如果连续{Y}次失败,立即报告

重新执行简化版任务。
```

## 4. 分阶段执行型提示词

### 模板4.1: 标准分阶段模板(防卡顿+可恢复) 🟡

**适用场景**: 任何超过3步的复杂任务(推荐默认使用)

**模板**:
```markdown
请帮我{在分支{branch-name}上 / 创建新分支{branch-name},然后}分阶段完成以下任务:

---

【阶段1: {阶段1名称}】(先执行,预计{X}分钟)

{任务描述}

完成后执行:
```bash
git add {相关文件}
git commit -m "阶段1-{简短描述}"
```

---

【阶段2: {阶段2名称}】(第二批执行,预计{X}分钟)

{任务描述}

**输入**: 阶段1的输出({具体文件/数据})

**输出**: {预期产出}

完成后执行:
```bash
git add {相关文件}
git commit -m "阶段2-{简短描述}"
```

---

【阶段3: {阶段3名称}】(第三批,预计{X}分钟)

{任务描述}

完成后执行:
```bash
git add {相关文件}
git commit -m "阶段3-{简短描述}"
```

---

【阶段N: ...】
[重复结构]

---

【执行建议】

1. **分批执行顺序**:
   - 第1次: 阶段1({X}分钟验证)
   - 第2次: 阶段2({X}分钟)
   - 第3次: 阶段3({X}分钟)
   - ...

2. **卡顿处理**:
   - 如果在阶段{X}卡住,先保存已完成的部分:
     ```bash
     git add .
     git commit -m "阶段{X}-部分完成"
     ```
   - 然后简化剩余任务或请求帮助

class AutoDesignWorkflow:
    def __init__(self, config):
        self.config = config
        self.prompt_template = load_template()
        self.logger = setup_logging()

    def run(self, input_params):
        # 步骤1: 准备
        validated_params = self.validate_input(input_params)
        self.logger.log("准备阶段完成")

        # 步骤2: 生成
        results = []
        for view_angle in self.config.angles:
            prompt = self.build_prompt(validated_params, view_angle)
            image = self.call_ai_api(prompt)
            results.append(image)
            self.logger.log(f"视角 {view_angle} 生成完成")

        # 步骤3: 后处理
        processed_results = self.post_process(results)
        report = self.generate_report(processed_results)

        return processed_results, report

    def build_prompt(self, params, view_angle):
        # 使用阶段1定义的提示词模板
        return self.prompt_template.format(
            vehicle_type=params['type'],
            view_angle=view_angle,
            style=params['style'],
            ...
        )

    def call_ai_api(self, prompt):
        # API调用逻辑 + 错误重试
        try:
            response = ai_api.generate(prompt)
            return response
        except RateLimitError:
            time.sleep(exponential_backoff)
            retry()

## 模板定制建议

### 如何调整模板适配你的场景

1. **添加领域特定检查点**:
   ```markdown
   # 在汽车设计任务中添加:
   - [ ] 比例检查: 车身长宽高比例符合{车型}标准
   - [ ] 风格一致性: 所有视角的设计语言统一
   ```

2. **自定义错误处理**:
   ```markdown
   # 针对你常遇到的错误类型:
   如果遇到{特定错误}:
   1. 检查{特定配置}
   2. 尝试{特定恢复方案}
   3. 记录到{你的错误知识库}
   ```

3. **整合你的工具链**:
   ```markdown
   # 如果你使用特定工具:
   在{阶段X}:
   - 导出到{你的CAD软件}格式
   - 验证与{你的渲染引擎}的兼容性
   ```

### 模板版本化

建议为你的定制模板建立版本控制:

```
prompt-templates/
├── official/           # 本文档的模板
│   ├── v1.0-basic.md
│   └── v2.0-advanced.md
└── custom/             # 你的定制版本
    ├── automotive-research-v1.2.md
    ├── workflow-build-v2.0.md
    └── CHANGELOG.md    # 记录每次优化的原因
```

每次使用后优化1-2处,在CHANGELOG中记录:
```markdown
## v1.2 (2025-01-15)
- 添加了汽车比例检查清单
- 优化了搜索关键词(更关注2024-2025年内容)
- 增加了导出到Blender的步骤
- 依据: 上次执行时发现比例问题,新增检查点预防
```
