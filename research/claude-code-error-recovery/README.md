## Top 5 实践建议(针对你)

### 1. 🎯 永远使用分阶段执行

**为什么**:
- 防止卡顿: 单阶段卡住不影响已完成部分
- 可恢复: 每个阶段有commit,失败时从checkpoint恢复
- 可审计: 清晰追踪每阶段的输入/输出
- **成功率>95%**: 社区验证的最佳模式

**使用模板**: [4.1 标准分阶段模板](./prompt-templates.md#模板41-标准分阶段模板防卡顿可恢复-)

**何时使用**: 任何超过3步的任务(推荐默认使用)

**实际效果**:
- 某遗留代码调试任务:数小时→几分钟
- 设计工作流构建:成功率70%→98%

---

### 2. 📊 标准任务必需日志

**为什么**:
- 出错可追溯: 日志中的错误上下文是恢复关键
- 优化有依据: 对比成功vs失败任务日志,提取关键指令
- 避免重复错误: 构建个人错误知识库

**使用模板**: [3.2 标准日志版](./prompt-templates.md#模板32-标准日志版推荐-)

**何时使用**:
- 网络搜索>2次
- 执行时间>10分钟
- 生产环境任务
- 需要团队协作的任务

**日志存储位置**: `logs/{task-type}/{task-name}-{YYYY-MM-DD}-execution.md`

**实战证明**: 5个案例中,日志都是快速定位问题根因的关键

### 3. ✅ 设置明确的成功标准

**为什么**:
- 防止任务范围扩散(Agent不会"善意"添加额外功能)
- 便于验证完成度
- 减少理解偏差

**实施方法**:
在提示词中明确"最终交付"清单:
```markdown
【最终交付】
- [ ] 具体交付物1(可验证)
- [ ] 具体交付物2(可验证)
- [ ] 具体交付物3(可验证)
```

**配合使用**:
- "只做"清单: 明确任务范围
- "不要做"清单: 明确禁止操作

**参考示例**: 见[模板2.2 任务范围重新界定](./prompt-templates.md#模板22-任务范围重新界定-)

### 4. 📚 建立个人模板库

**为什么**:
- 成功模式可复用: 避免每次重新设计提示词
- 持续优化: 每次使用后迭代改进
- 节省时间: 标准任务从构思到执行时间减少50%+

**实施步骤**:

1. **初始化结构**:
```
your-templates/
├── official/           # 本项目的14个模板
├── custom/             # 你的定制版本
│   ├── research-task-v1.0.md
│   ├── workflow-build-v1.0.md
│   └── automotive-specific-v1.0.md
└── CHANGELOG.md        # 记录每次优化
```

2. **分类方法**:
- 按任务类型: 调研类、构建类、测试类、汽车设计专用
- 按复杂度: 简单(5分钟)、标准(10-30分钟)、复杂(>30分钟)

3. **迭代优化**:
每次使用后:
- 记录哪些部分有效、哪些需要调整
- 更新模板版本号(如v1.0→v1.1)
- 在CHANGELOG中记录优化原因

**长期收益**:
- 3个月后: 拥有10+个经过验证的个人模板
- 6个月后: 标准任务成功率>90%,执行时间减半

### 5. 🧪 先小后大的测试策略

**为什么**:
- 避免大任务卡顿浪费时间
- 快速验证提示词有效性
- 及时发现问题并调整

**实施步骤**:

1. **用简化版任务测试提示词**(阶段1):
   - 例如: 完整任务是"调研10个工具",先用"调研2个工具"测试
   - 验证点: 提示词结构是否清晰、日志是否按预期生成

2. **验证日志清晰度**:
   - 检查日志是否记录了关键决策点
   - 确认错误处理逻辑是否触发

3. **再执行完整任务**:
   - 基于测试结果优化提示词
   - 执行完整版本

**时间对比**:
- 不测试直接执行大任务: 卡顿后需要从头开始,总耗时X+Y
- 先测试小任务: 测试时间0.2X,调整后执行0.8X,总耗时X
- **节省**: 避免浪费Y时间(Y通常是X的50%-100%)

**适用场景**:
- 首次使用新模板
- 复杂的网络搜索任务
- 生产环境关键任务

## 常见问题(FAQ)

### Q1: Claude Code还是卡住了怎么办?

**A**: 分阶段执行+日志记录的组合应对:

1. **立即停止,不要等待**:
   - 如果2分钟没有进展,中断当前操作

2. **检查日志**:
   - 定位最后一次成功的操作
   - 识别卡在哪个阶段

3. **保存当前进度**:
   ```bash
   git add .
   git commit -m "阶段X-部分完成(卡顿前保存)"
   ```

4. **简化任务**:
   - 将卡住的阶段拆分为更小的子任务
   - 或跳过该阶段,先完成其他部分

5. **使用错误恢复模板**:
   - [模板2.1](./prompt-templates.md#模板21-错误分析与恢复-): 诊断卡顿原因
   - 常见原因: 任务过于复杂、缺少明确指令、网络搜索过多

6. **预防措施**:
   - 下次使用[模板4.1](./prompt-templates.md#模板41-标准分阶段模板防卡顿可恢复-)
   - 在提示词中明确:"每阶段预计时间不超过{X}分钟"

---

### Q2: 日志文件太多怎么管理?

**A**: 参考[日志存储策略](./logging-best-practices.md#日志存储策略)

**推荐的目录结构**:
```
logs/
├── research/          # 按任务类型分类
│   ├── task-A-2025-01-15-execution.md
│   └── task-B-2025-01-16-execution.md
├── feature-development/
├── debugging/
└── archive/
    ├── 2024-12/       # 按月归档
    └── 2025-01/
```

**清理策略**:
- **保留期**:
  - 最近30天: 保留所有日志
  - 30-90天: 保留标准日志,删除详细审计
  - >90天: 仅保留错误日志和关键任务审计
- **压缩**: 归档日志使用`gzip`压缩
- **索引**: 维护`logs/INDEX.md`快速索引

**自动化脚本**(可选):
```bash
# 每月1号运行
#!/bin/bash
# 归档上个月的日志
LAST_MONTH=$(date -d "last month" +%Y-%m)
mkdir -p logs/archive/$LAST_MONTH
mv logs/*/$LAST_MONTH-*.md logs/archive/$LAST_MONTH/
gzip logs/archive/$LAST_MONTH/*.md
```

### Q3: 如何判断任务是否需要分阶段?

**A**: 使用这个决策标准:

**必需分阶段** (使用模板4.1或4.2):
- ✅ 任务步骤 >3个
- ✅ 预计执行时间 >10分钟
- ✅ 包含网络搜索
- ✅ 多个独立的子任务(如调研+实现+测试)
- ✅ 生产环境任务

**可选分阶段** (可用模板1.2):
- 🟡 任务步骤 =3个
- 🟡 预计执行时间 5-10分钟
- 🟡 可能遇到中间错误

**无需分阶段** (使用模板1.1):
- ❌ 单文件编辑
- ❌ 简单配置修改
- ❌ 预计执行时间 <5分钟
- ❌ 已验证的重复性任务

**经验法则**:
- "如果不确定是否需要分阶段,那就分阶段" - 成功率更高
- 分阶段的额外成本很小(多写几行提示词),但收益巨大(防卡顿+可恢复)

### Q5: 如何从错误中学习,避免重复犯错?

**A**: 建立"错误-恢复"知识库

**步骤1: 记录错误**:
每次遇到错误时,在日志中记录:
- 错误类型(参考[错误类型分类](./error-types-and-recovery.md))
- 触发操作
- 恢复方式
- 是否成功

**步骤2: 定期回顾**(每周或每月):
1. 统计错误类型分布
2. 找出Top 3高频错误
3. 分析根因:
   - 提示词不够明确?
   - 缺少某个检查点?
   - 对Claude Code的能力边界理解有误?

**步骤3: 创建预防模板**:
为高频错误创建专门的预防模板,例如:

```markdown
# 预防模板: API超时
每次调用外部API时,在提示词中加入:

错误处理:
- 如果遇到API超时,自动重试3次
- 重试间隔: 2s, 4s, 8s (指数退避)
- 3次失败后,保存当前进度并报告

来源: 根据2025-01-10日志,API超时在批量任务中出现3次
```

**步骤4: 构建知识库**:
```
knowledge-base/
├── error-patterns/
│   ├── api-timeout-recovery.md (基于10次相似错误的总结)
│   ├── git-conflict-resolution.md
│   └── rate-limit-handling.md
├── optimization-insights/
│   ├── search-efficiency.md (Grep vs Bash grep性能对比)
│   └── batch-processing.md (最优批次大小分析)
└── prompt-templates/
    └── automotive-research-v2.1.md (基于5次成功任务优化)
```

**长期效果**:
- 3个月后: 重复错误减少70%
- 6个月后: 建立20+个验证过的预防模板
- 1年后: 成功率>95%,执行时间减少50%

### Q6: 如何选择日志级别?

**A**: 根据任务特征快速决策:

**Level 1: 最小日志** (使用模板3.1)
- ✅ 适用: 简单任务、已验证的重复任务、执行时间<5分钟
- ✅ 优势: 快速、不影响执行效率
- ❌ 不适用: 首次执行的任务、复杂任务、需要优化的任务

**Level 2: 标准日志** (使用模板3.2) - **推荐默认**
- ✅ 适用: 多阶段任务、网络搜索、生产环境、团队协作
- ✅ 优势: 平衡详细度和效率,记录关键决策点
- ✅ 记录内容: 每阶段输入/输出、错误上下文、工具调用
- 📊 推荐指数: ⭐⭐⭐⭐⭐

**Level 3: 详细审计** (使用模板3.3)
- ✅ 适用: 生产环境关键任务、需要后续优化的工作流、安全审计
- ✅ 优势: 完整追溯、性能分析、可复现
- ✅ 记录内容: 决策树、工具调用明细、中间状态快照、性能指标
- ⚠️ 成本: 需要额外时间记录,适合高价值任务

**快速决策表**:

| 任务特征 | 推荐日志级别 |
|---------|------------|
| 执行时间<5分钟 | Level 1 |
| 执行时间5-30分钟 | Level 2 |
| 执行时间>30分钟 | Level 2或3 |
| 网络搜索>2次 | Level 2 |
| 生产环境部署 | Level 2或3 |
| 需要性能优化 | Level 3 |
| 安全审计需求 | Level 3 |

**经验法则**:
- "不确定时选Level 2" - 适合90%的任务
- "关键任务用Level 3" - 值得投入额外时间
- "简单重复任务用Level 1" - 提高效率

2. **创建日志目录**:
   ```bash
   mkdir -p logs/{research,feature-development,debugging,workflows}
   mkdir -p logs/archive
   ```

3. **测试模板**:
   - 选择一个小任务(预计5-10分钟)
   - 使用模板4.1+3.2执行
   - 验证日志记录是否清晰

### 本周内(1小时)

1. **整理成功提示词**:
   - 回顾过去成功的3个任务
   - 提取关键指令和结构
   - 归档到个人模板库:
     ```
     your-templates/
     ├── successful-case-1.md
     ├── successful-case-2.md
     └── successful-case-3.md
     ```

2. **针对高频任务定制模板**:
   - 识别你的Top 3高频任务类型(如调研、工作流构建、测试)
   - 基于本项目的14个模板,定制3个专用模板
   - 示例:
     ```markdown
     # 我的汽车设计调研模板 v1.0
     [基于模板5.3定制]

     搜索关键词:
     - "{topic} automotive design 2024 2025"
     - "{topic} car rendering best practices"
     - "{topic} automotive industry case study"

     特殊要求:
     - 优先查找支持参数化设计的工具
     - 评估与Blender的兼容性
     - 关注高精度渲染能力
     ```

3. **建立"提示词版本控制"习惯**:
   - 创建CHANGELOG.md:
     ```markdown
     # 提示词优化记录

     ## 汽车设计调研模板

     ### v1.1 (2025-01-16)
     - 优化: 增加了"与现有工具集成"检查点
     - 原因: 上次执行时忽略了Blender兼容性,导致后期返工
     - 效果: 成功率提升到90%

     ### v1.0 (2025-01-15)
     - 初始版本,基于模板5.3
     ```

### 长期(持续优化)

1. **每月回顾日志**(30分钟):
   - 打开`logs/`目录,筛选上月的所有日志
   - 统计:
     * 成功vs失败任务比例
     * Top 3错误类型
     * 平均执行时间
   - 识别重复错误模式:
     ```markdown
     # 2025年1月日志分析

     总任务数: 20
     成功: 17 (85%)
     失败: 3 (15%)

     Top 3错误:
     1. API超时(2次) - 原因: 批量任务未设置节流
     2. 范围扩散(1次) - 原因: 提示词未明确"不要做"清单

     改进措施:
     - 在所有批量任务模板中加入节流参数
     - 更新模板,强制包含"不要做"清单
     ```
